### 4.2 ⚠️ 有 tenant_id 但无过滤 (2个) — 高风险

#### api-key-service

```
问题: models.rs 中定义 tenant_id 字段，但 repository.rs 所有查询仅用 user_id 过滤
受影响查询:
  - FROM api_keys WHERE id = $1 (按主键查，无租户过滤)
  - FROM api_keys WHERE user_id = $1 (按用户查，无租户过滤)
  - FROM api_key_usage_logs WHERE key_id = $1 (按 key_id 查，无租户过滤)
风险: 知道 key_id 的用户可能跨租户访问 API Key
```

#### file-service

```
问题: models.rs 中定义 tenant_id 字段，但 repository.rs 查询无租户过滤
受影响查询:
  - FROM sys_files WHERE id = $1 AND deleted_at IS NULL
  - FROM sys_files WHERE id = ANY($1) AND deleted_at IS NULL
风险: 知道 file_id 的用户可访问任意租户的文件
```

## 五、关键风险发现

### 🔴 高风险

1. **api-key-service 跨租户访问**: 模型有 tenant_id 但 SQL 未使用，API Key 查询仅按 user_id 或 key_id
2. **file-service 跨租户文件访问**: 文件查询按主键/ID，无租户隔离
3. **workflow-service 无租户隔离**: 285行数据库访问代码，完全无 tenant_id

### 🟡 中风险

4. **tenant_extraction_middleware 未注册**: api-gateway 已定义但未使用，导致无法自动注入 TenantContext
5. **tenant-core thread-local 传播限制**: 跨 .await 点上下文丢失
6. **messaging-service/social-ops-service**: 仅按 user_id 过滤，若 user_id 可能重复跨租户则有风险

### 🟢 低风险

7. **user-service**: 无租户字段，但可能是共享用户池的合理设计
8. **audit-service**: 审计日志通常需要全局访问
