## 三、tenant-core crate 分析

### 3.1 核心组件

| 文件 | 功能 | 状态 |
|------|------|------|
| `context.rs` | TenantContext 结构体 + thread-local 上下文管理 | ✅ 完整 |
| `middleware.rs` | Axum Layer 实现（TenantLayer, RequireTenantMiddleware） | ✅ 完整 |

### 3.2 TenantContext 功能

- 存储 tenant_id、user_id、roles、permissions
- 提供 `current_tenant_id()` 获取当前租户
- 提供 `is_platform_admin()` 判断平台管理员

### 3.3 已知限制

- `with_tenant_context` 使用 thread-local，注释明确标注**不保证跨 .await 传播**
- 需要使用 `tokio::task_local!` 实现真正的异步传播

## 四、各服务租户隔离状态

### 4.1 ✅ 已实施租户隔离 (3个)

| 服务 | 模型 tenant_id | SQL WHERE tenant_id | 说明 |
|------|---------------|---------------------|------|
| billing-service | ✅ `tenant_id: Uuid` | ✅ 4处 WHERE 过滤 | 订阅/用量查询均过滤 |
| pay-service | ✅ `tenant_id: i64` | ✅ 4处 WHERE 过滤 | 订阅查询过滤 |
| tenant-service | ✅ `tenant_id: i64` | ✅ 含隔离管理器 | 核心租户管理服务 |

### 4.2 ⚠️ 有 tenant_id 但无过滤 (2个) — 高风险

#### api-key-service

- **模型**: `ApiKey` 结构体含 `tenant_id: i64`
- **SQL 查询**: 所有 repository 方法均未使用 `tenant_id` 过滤
- **风险**: 任何持有有效 API Key 的用户可访问其他租户的密钥数据
- **修复**: `list_keys` 方法需添加 `.filter(tenant_id.eq(...))`

#### file-service

- **模型**: `FileRecord` 结构体含 `tenant_id: i64`
- **SQL 查询**: `list_files` 和 `get_file_by_id` 未使用 `tenant_id` 过滤
- **风险**: 用户可通过文件 ID 访问其他租户的文件记录
- **修复**: 所有查询方法需添加 `tenant_id` 过滤

### 4.3 ❌ 无 tenant_id 字段 (12个)

auth-service, user-service, audit-service, cms-service, messaging-service, workflow-service, feedback-service, social-ops-service, browser-service, hik-service, lpr-service, ctp-service, ebike-service, tow-service, clean-service, xlt-service, api-gateway

> **说明**: 这些服务要么无数据库访问（纯 HTTP/gRPC 透传），要么其数据模型设计为平台级共享（如 audit_logs 平台级审计、tenant-service 本身是租户管理入口）。

### 4.4 🚫 需要特别关注

| 服务 | 风险等级 | 说明 |
|------|---------|------|
| workflow-service | 🟠 中 | 285 行数据库代码，业务数据但无 tenant_id 过滤 |

## 五、修复建议

### 5.1 立即修复 (高风险)

1. **api-key-service**: 在 `list_keys` 方法中添加 `tenant_id` 过滤
2. **file-service**: 在 `list_files` 和 `get_file_by_id` 方法中添加 `tenant_id` 过滤
3. **api-gateway**: 在 `route_builder.rs` 中注册 `tenant_extraction_middleware`

### 5.2 短期改进 (中风险)

4. **tenant-core**: 将 thread-local 替换为 `tokio::task_local!` 实现跨 .await 传播
5. **workflow-service**: 审查数据模型是否需要添加 `tenant_id` 字段

### 5.3 长期完善

6. **CI 集成测试**: 添加多租户隔离测试套件
7. **Schema 路由**: 评估是否采用 PostgreSQL Schema 级隔离替代行级过滤

## 七、结论

erp_new 的多租户隔离框架已搭建（tenant-core crate），但实际覆盖率仅 **14% (3/21)** 的服务实施了行级 `tenant_id` 过滤。最高优先级是修复 api-key-service 和 file-service 的跨租户数据泄露风险，这两个服务存储了敏感业务数据（API 密钥、文件记录）却未实施隔离。
